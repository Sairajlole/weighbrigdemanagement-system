# Tulanam Weighbridge — Security & Correctness Audit

**Date:** 2026-06-13
**Scope:** Flutter desktop client + Firebase (Cloud Functions, Firestore rules/indexes), repo `/Users/yashkawdiya/IdeaProjects/weigh`.

## Executive Summary

This audit ran 14 review cells across the auth/MFA backend, Firestore rules, the setup wizard, the weighment/camera path, integrations/print, offline/backup, operators/customers/reports, and platform divergence. Of **124 raw findings, 118 were confirmed** after skeptic filtering; **11 originally-high findings were refuted or downgraded** and **7 new high/critical survived**. The two top risks are both in `firestore.rules`: the live ruleset (identical to `firestore.rules.bak`, the tightened version is undeployed) leaves tenant collections and operator docs world read/write, and `operatorUpdateSafe()` omits `passwordHash` from its blocklist — combined with `loginUser`'s legacy-SHA-256 fallback this is a **server-mintable session-token account-takeover** on any account before its first login-migration. The other survivors cluster in auth revocation (sessions outlive deletion/demotion), MFA re-enrollment takeover, a Windows login path that skips 2FA entirely, PowerShell command injection via operator-editable printer names, and an offline-queue bug that turns integration retries into phantom duplicate weighments. A large medium/low tail is dominated by Flutter set-state-after-dispose / controller-leak lifecycle defects and unbounded client-side Firestore reads. Memory notably claimed the client `passwordHash` writes were removed (auth-security.md:36) — **the tree shows they were reverted or never landed**, and the `notifications write:if true` regression is still live.

## A. New high-impact (confirmed)

Ranked critical > high; all confidence = high, so intra-tier order is free.

#### [CRITICAL] operatorUpdateSafe() does not block passwordHash → client operator-update enables auth bypass via loginUser legacy branch
`firestore.rules:11-14, 38-41, 170-173` (+ `functions/index.js:458-468`, `account_step.dart:25,1021/1031`) · security · confidence: high · skeptic: 3/3 upheld

**Evidence**
```
operatorUpdateSafe() blocklist = ['role','pinHash','activeSessionId','uid','isAdmin','isCompanyAdmin','mfaRequired']  // passwordHash NOT listed
loginUser (index.js:458-468): if no credentials/{email} doc → ok = _legacySha256(password) === docData.passwordHash
_legacySha256(p) == _hashPassword(p) == sha256(utf8(password))  // identical
```
**Impact** An attacker reaching the (anonymous-writable) operator-doc update path sets `passwordHash = sha256(attacker_pw)`; the diff touches only `passwordHash` so `operatorUpdateSafe()` returns true. `loginUser` then matches the legacy branch and **mints a real session token for ANY account lacking a `credentials/{email}` doc** — i.e. every account registered via `account_step` until its first login-migration. Broad pre-first-login takeover surface, not just true-legacy accounts.

**Fix** Add `passwordHash` (and `hasPin`,`emailVerified`,`isActive`, etc.) to the `operatorUpdateSafe()` blocklist in all three operator match blocks; better, stop the client writing `passwordHash` to operator docs and have `loginUser` verify only against `credentials/`, gating any `doc.passwordHash` fallback behind a server-set migration flag. *(See C — memory claimed these client writes were removed; tree shows they were not.)*

#### [CRITICAL] Broad if-true tenant collections + {path=**}/operators read:if true expose operator docs cross-tenant
`firestore.rules:24-25, 43-45, 88, 117, 164-166` · security · confidence: high · skeptic: 3/3 upheld

**Evidence**
```
match /{path=**}/operators/{operatorId} { allow read: if true; }   // 164-166
customers (43-45), settings (24-25,175-177), sites (88), weighments create/update (117), materials → read,write: if true
diff firestore.rules firestore.rules.bak  →  identical (tightened ruleset is undeployed)
```
**Impact** Live rules leave customers/settings/weighments(create,update)/sites/materials world read+write, and all operator docs world-readable via the recursive wildcard — cross-tenant read+write plus operator-doc field exposure (`passwordHash` + PII; `pinHash` is now in server-only `operator_pins/` for migrated operators, but unmigrated docs may still carry it for up to 1 hr until `sweepPinHashes` runs).

**Fix** Deploy `firestore.rules.tightened` once the `companyId` custom-claim is confirmed in the live token and the flat-operators write migration is done. Note Linux has no Firebase plugins, so a `request.auth`/claims rewrite needs claims plumbing that does not yet exist.

#### [HIGH] Session tokens survive account deletion / deactivation / role demotion (revocation bypass)
`functions/index.js:398-410, 413-422, 863, 923-981` · security · confidence: high · skeptic: 2/3 upheld

**Evidence**
```
_requireSession (398-410): checks only token existence + 30-day TTL, returns {email,companyId,role} frozen at mint time
auth_sessions referenced ONLY at 383/387 (mint) and 401 (require) — appears NOWHERE in onOperatorDeleted (923-981) or onOperatorUpdated (863)
onOperatorDeleted deletes the Auth account + face frames but never deletes auth_sessions docs
isActive true→false (863) and role-change (895) branches only write audit logs + notifications
```
**Impact** A deleted/deactivated operator or a demoted admin keeps a fully valid token for up to the 30-day TTL, retaining API access to session-guarded callables (`triggerGate` 1554, etc.) and — because `_requireAdminSession` trusts the frozen role — retaining ADMIN rights after demotion. A revocation bypass on the core auth path.

**Fix** On `onOperatorDeleted` and the isActive/role/isArchived branches of `onOperatorUpdated`, delete the account's `auth_sessions` docs (query by email). Additionally, have `_requireSession`/`_requireAdminSession` re-load the live operator/company doc and re-check `isDeleted`/`isActive`/`isArchived` and current role rather than trusting mint-time values.

#### [HIGH] Password-only MFA re-enrollment takeover: mfaConfirmEnroll rebinds 2FA without the existing second factor
`functions/index.js:608-666` · security · confidence: high · skeptic: 3/3 upheld

**Evidence**
```
mfaBeginEnroll (608-626): verifies ONLY the password, then writes mfaPendingSecret regardless of mfaEnabled===true
mfaConfirmEnroll (632-667): checks only mfaPendingSecret + 10-min expiry + _verifyTotp(pending, code);
   never reads cred.mfaEnabled, never requires the CURRENT authenticator/backup code;
   writes mfaEnabled:true, mfaSecret:pending, mfaBackupCodes:... with {merge:true}
```
**Impact** An attacker with a stolen password but not the victim's authenticator can `mfaBeginEnroll → load fresh secret into their own app → mfaConfirmEnroll`, rebinding `mfaSecret` and backup codes to their device. This defeats the second factor with the password alone — the exact threat `mfaDisable` was hardened against, bypassed by *re-binding* instead of disabling. `_notifyMfaChanged` is detection, not prevention.

**Fix** When `cred.mfaEnabled===true`, require the current second factor (valid existing TOTP or unused backup code against the active `mfaSecret`) before begin/confirm may overwrite the secret, or refuse re-enrollment until MFA is first disabled via `mfaDisable`. Also bind these callables to a session token.

#### [HIGH] Windows login path bypasses TOTP 2FA and single-session enforcement (loginUser never called)
`lib/features/setup/presentation/steps/welcome_step.dart:966-1077` · security · confidence: high · skeptic: 3/3 upheld

**Evidence**
```
_submit (966): if (Platform.isWindows) _submitWindows(...) else _submitDefault(...)
_submitWindows (989): only signInWithEmailAndPassword (993-996) + Firestore lookups; never calls loginUser/loginUserWithMfa
_submitDefault (1080): calls loginUserWithMfa (1094) → _storeSessionToken sets/persists sessionToken
```
**Impact** On Windows the custom TOTP gate lives entirely in `loginUser`, which `_submitWindows` never invokes — an account with 2FA enabled signs in with email+password only, second factor skipped. No session is minted (no single-session enforcement), and any `_requireSession`-guarded callable rejects the Windows user. The bypass still has teeth: an attacker with email+password (not the TOTP secret) gets into the app and can drive non-session-gated callables (e.g. `verifyOperatorPin` index.js:6835). `loginUser` is NOT platform-blocked — `lock_screen.dart:155` routes it over HTTP on Windows/Linux — so this is an omission, not a platform limitation.

**Fix** Call `loginUserWithMfa` (HTTP transport) in `_submitWindows` exactly as `_submitDefault` does, before navigating, store the returned `sessionToken`/`activeSessionId`, and treat its failure as fatal.

#### [HIGH] PowerShell command injection via operator-controlled printer name on Windows print path
`lib/shared/services/print_service.dart:1382-1386` (also 1337, 639) · security · confidence: high · skeptic: 3/3 upheld

**Evidence**
```
_tryBackupPrinter (1383-1385): Process.run('powershell', ['-NoProfile','-Command',
  'Start-Process -FilePath "${tmpFile.path}" -Verb PrintTo -ArgumentList "$backupPrinter" -Wait -WindowStyle Hidden'])
_sendPdfToLpr:1337 ('...-ArgumentList "$printer"...') and _sendBinaryRawToLpr:639 ('...Out-Printer -Name "$printer"...') — same unescaped -Command interpolation
printer nickname is operator-editable free text: printing_screen.dart:3143 onChanged: (v) => printers[e.key]['nickname'] = v
```
**Impact** A nickname/backupPrinter like `x"; Start-Process calc; "` is interpolated into a PowerShell `-Command` string and executes arbitrary PowerShell on the weighbridge PC under the app's privileges; benign names containing `"` or `$` silently break printing. Operators are lower-privilege users, so this is privilege-relevant. Affects three print paths (1337, 639, 1385).

**Fix** Never build PowerShell from concatenated untrusted values. Pass the printer name via `-Args`/a bound variable, or strictly allowlist the resolved name against the OS-enumerated `Win32_Printer.Name` list. At minimum escape `"`, backtick, and `$`. Apply to `_sendPdfToLpr`, `_sendBinaryRawToLpr`, `_tryBackupPrinter`.

#### [HIGH] Integration-retry payloads queued as weighments create phantom duplicate weighment docs (silent data corruption)
`lib/shared/services/offline_queue_service.dart:123-153` (producers `post_weighment_service.dart:58,62,80,84`) · data-loss · confidence: high · skeptic: 2/3 upheld

**Evidence**
```
Producers: _queue.enqueueWeighment({'_retryType':'sheets', ...weighmentData})   // also 'billing'
_flushWeighments(): removes enqueuedAt, converts timestamps, then paths.weighments.add(raw); file.delete()
   — never branches on '_retryType' ('_retryType' written in 4 places, read in 0)
```
**Impact** `PostWeighmentService` runs after the weighment is already saved; on a failed Sheets/billing call it enqueues the full payload tagged `_retryType` via `enqueueWeighment` (the only caller). `_flushWeighments` ignores the tag and calls `weighments.add(raw)`; permissive rules accept it with no field validation. Net effect: (a) the real Sheets/billing retry never happens, and (b) every queued retry becomes a phantom duplicate weighment (with `_retryType` persisted), inflating counts/tonnage/billing/serial sequences. Auto-replays every 10 s.

**Fix** Do not route integration retries through `enqueueWeighment`. Add dedicated queue types (`sheets_retry`,`billing_retry`) with flush handlers that re-call the Sheets/billing service — never `weighments.add`. At minimum, branch on `raw['_retryType']` in `_flushWeighments` and strip it before any write.
